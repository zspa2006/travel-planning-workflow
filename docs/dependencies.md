# 六人分工依赖与联调顺序

**六人可以并行开工。接口预留属于协作约定，表中顺序只用于安排真实联调。** A、B 用样例数据独立验收界面，D 用模拟节点验证调度，E 用行程样例验证规则，F 用需求样例验证输出。进入真实联调时，C 优先交房间和偏好接口，D 优先交可运行的事件流，E 和 F 优先交可覆盖异常场景的规则与结构化产物。

| 上游 → 下游 | 尽早交付的内容 | 阻塞的真实联调 |
| --- | --- | --- |
| C → A | 会话、房间、成员、偏好、方案接口与权限样例 | 建房、加入、刷新后恢复及方案展示 |
| C ↔ E | 方案 ID、候选与正式版本、投票存储和发布事务边界 | 多数票结算、旧运行覆盖保护 |
| C → D | 房间输入快照和持久化接口 | 启动规划、记录候选和发布结果 |
| F → D、E、C | AgentRequest/AgentResult、行程 JSON、来源/可信状态、缺价和错误样例 | 调度真实节点、六类校验、方案入库 |
| E → D | 校验问题码、阻塞/警告、返工与人工确认结果 | 异常分支、候选入库及发布门控 |
| E → A、B | 版本状态、人工确认和投票契约 | A 的候选/正式展示及 B 的投票和门控 |
| D → B | DAG 节点、运行快照、事件序号、控制操作和失败样例 | 实时状态、重连、暂停/继续/取消 |

## 真实联调顺序

1. **接口会。** C 发房间和方案样例，E 定状态与问题码，F 发结构化行程与失败样例，D 发快照和事件样例。共同定版本键、金额单位和缺价语义。C 与 E 的交叉依赖在契约评审中收敛，双方按同一契约并行开发。
2. **基础链路。** C 优先实现认证 → 房间/成员 → 偏好保存 → 方案读取。A 用样例和本地适配器完成前端后，尽早切换 HTTP 适配器验证两账号隔离和刷新持久化。B 同步以 D 的事件样例做可视化。
3. **规划与规则。** F 优先提供可解析的模拟输出，E 用同样样例实现确定性校验和发布守卫，D 先用模拟节点跑通 DAG、有限重试和控制事件。D 有可运行的事件流后即可与 B 联调，真实模型和地图可随后替换模拟节点。
4. **发布闭环。** C、D、E 验证候选存储、等待投票、通过后原子发布；A 核对刷新后的正式版本，B 核对最终状态和异常事件。

全链路最终依赖 C 的数据底座、F 的结构化产物、E 的门控和 D 的调度。四项都需要提前交一份可联调版本。没有各模块工期和成员排期，当前只能确定依赖先后及阻塞点。

F 的节点契约、模拟失败样例、六类校验证据和持久化字段见 [F 智能体与地图接口](agent-api.md)。
